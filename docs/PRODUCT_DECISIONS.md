# 店小服｜产品迭代与关键决策

本文记录店小服从“能回答电商问题”到“能在订单、规则和状态边界内完成服务”的产品取舍，用于说明产品定位、功能边界与评测设计之间的关系。

## 1. 先让用户开口，再让订单成为执行锚点

**问题：** 消费者通常从“我要退”“催一下”“这个有问题”等短句开始，但一位用户可能有多笔订单。若所有问题都要求先进入订单页，会增加咨询门槛；若只按文本猜测订单，又可能查询或处理错误对象。

**选择：** 商品与政策问题支持直接在对话中发起；涉及订单、物流、地址、取消或售后处理时，引导用户选择或绑定本人订单。

**暂缓方案：** 所有服务都从订单表单开始；或允许模型仅根据用户文本猜测要处理的订单。

**取舍：** 对话入口降低了第一次表达的门槛，订单锚定保证了后续查询和写入的对象准确。对象不明确时，用户需要多一次选择或澄清。

**验证信号：** `release-v1` 将订单匹配作为独立断言；发布运行的订单匹配正确率为 **100%**。

## 2. 对高影响动作采用“说明—确认—校验”链路

**问题：** “确认”“不要了”“改成这个”等短回复可能指向不同的订单和动作。取消订单、修改地址、物流拦截和售后提交会影响用户权益与履约状态。

**选择：** 系统先展示目标订单、金额、地址或处理影响，收到明确确认后，再由服务端校验订单归属、当前状态和待办动作并执行。

**暂缓方案：** 仅依据关键词或前端按钮直接写入；让模型自行生成业务写入参数。

**取舍：** 多一步交互换取更低的误操作风险；确认只在当前订单、当前动作和当前上下文中有效。

**验证信号：** 评测覆盖孤立确认、否定、诉求切换、地址不完整、取消与拦截；发布运行的关键操作安全率为 **100%**。

## 3. 用售后记录承接跨页面进度，而非只保存聊天文本

**问题：** 对话适合解释和追问，但无法稳定承载补材料、审核、退货单号和退款阶段。消费者在聊天、售后页和通知入口之间切换时，需要看到同一进度。

**选择：** 将售后申请和时间线作为状态真值；对话状态卡、售后记录、通知和审核任务围绕同一申请同步。

**暂缓方案：** 只在聊天文本中维护进度；各页面各自维护本地状态。

**取舍：** 状态协调成本更高，但刷新、重新登录和审核回写后仍能恢复连续体验。

**验证信号：** 售后记录页支持填写退货单号和查看时间线；审核决定同步到消费者对话、售后记录与通知。

## 4. 商品问题先收集凭证，再进入人工审核

**问题：** 破损、少件、错发等问题通常不能只凭一句描述决定退款、换货或补发；审核员需要看到与订单关联的图片和上下文。

**选择：** 对商品问题引导上传图片凭证；材料不足时进入等待补充材料，补齐后回到审核队列，并保留原对话和历史记录。

**暂缓方案：** 由模型根据文字描述直接判定商品问题；让用户重新创建与原对话脱离的新工单。

**取舍：** 用户需要额外提供材料，审核员获得更完整的判断依据，原申请也能持续承接上下文。

**验证信号：** 消费者端支持 JPG/JPEG/PNG/WEBP/GIF 图片凭证；审核任务展示附件与会话；评测覆盖凭证与补材料路径。

## 5. 用范围门禁保持客服入口聚焦

**问题：** 开放输入会把技术、金融、作业等无关问题带入客服会话，既消耗模型能力，也会模糊商品、订单、物流和售后的服务定位。

**选择：** 在进入模型前识别非电商范围请求，并将用户引导回店铺商品、订单、物流和售后服务。

**暂缓方案：** 将客服入口作为通用知识问答；让模型自由决定是否回答无关问题。

**取舍：** 服务入口更聚焦，同时需要持续维护对泛商品咨询与真正非服务问题的区分。

**验证信号：** `release-v1` 包含非电商范围与提示注入用例；发布运行的非电商范围门禁绕过率为 **0%**。
